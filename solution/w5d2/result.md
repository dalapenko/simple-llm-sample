# RAG: Реализация, Оценка и Демонстрация

---

## 1. Что такое RAG и зачем он нужен

**RAG (Retrieval-Augmented Generation)** — это архитектурный паттерн, при котором перед вызовом LLM система сначала *извлекает* релевантный контекст из локального хранилища, а затем *дополняет* им пользовательский запрос.

### Проблема без RAG

Большие языковые модели обладают огромными знаниями общего характера, но **не знают** деталей конкретного проекта: имён конкретных файлов, значений конкретных констант, внутренней архитектуры вашей кодовой базы. Без RAG модель:

- **Галлюцинирует** — придумывает правдоподобные, но ложные ответы
- **Отвечает обобщённо** — даёт типичные ответы для «среднестатистического проекта»
- **Не может цитировать источники** — нет привязки к конкретному файлу/строке

### Решение с RAG

1. **Индексация** — документы разбиваются на фрагменты (chunks), каждый фрагмент векторизуется через embedding-модель и сохраняется в SQLite
2. **Поиск** — запрос пользователя тоже векторизуется, затем через косинусное сходство находятся top-K наиболее близких фрагментов
3. **Дополнение контекста** — найденные фрагменты вставляются в промпт с метаданными (имя файла, раздел)
4. **Ответ** — LLM отвечает, опираясь на *реальные данные из кода*, а не на статистику обучения

## 2. Архитектура реализации

### Схема потока данных

```
Пользователь вводит вопрос
        ↓
   RagService.augment(query)
        ↓
   SearchService.findSimilar(query, topK=5)
        ↓
   OpenRouterEmbeddingClient.embed(query)   →   FloatArray[1536]
        ↓
   SqliteVectorStore.search(embedding, 5)   →   cosine similarity → top-5
        ↓
   ContextAssembler.assemble(entries)       →   "Источник: Файл.kt, Раздел: X:\n..."
        ↓
   buildRagPrompt(context, query)
        ↓
   ConversationManager.sendMessage(augmented)
        ↓
        LLM (claude-sonnet / gpt-4o / ...)
```

### Ключевые компоненты

| Компонент                   | Модуль     | Назначение                              |
|-----------------------------|------------|-----------------------------------------|
| `SearchService`             | `:indexer` | embed(query) + vectorStore.search()     |
| `ContextAssembler`          | `:indexer` | Форматирует фрагменты с метаданными     |
| `RagService`                | `:cli-app` | Оркестрирует поиск + сборку промпта     |
| `SqliteVectorStore`         | `:indexer` | Косинусное сходство по всем векторам    |
| `OpenRouterEmbeddingClient` | `:indexer` | text-embedding-3-small (1536 измерений) |

### RAG-промпт (шаблон)

```
Используй предоставленный контекст для ответа на вопрос.
Если в контексте нет ответа, так и скажи.

Контекст:
Источник: FixedSizeChunker.kt, Раздел: FixedSizeChunker:
class FixedSizeChunker(
    private val chunkSize: Int = 500,
    private val overlapPct: Float = 0.12f
...

---

Источник: IndexPipeline.kt, Раздел: IndexPipeline:
...

Вопрос: <оригинальный вопрос пользователя>
```

### Флаги запуска CLI

```bash
# Без RAG (по умолчанию)
./gradlew :cli-app:run

# С RAG
./gradlew :cli-app:run --args="--rag"

# Явное отключение RAG
./gradlew :cli-app:run --args="--no-rag"
```

## 4. Сравнительная таблица RAG vs. Без RAG

### Вопрос 1: Размер фрагмента в FixedSizeChunker

**Ответ без RAG:**
> "В большинстве реализаций chunk size составляет 256 или 512 токенов. По умолчанию часто используют 512 токенов для оптимального баланса между точностью и контекстом."

**Ответ с RAG:**
> "В `FixedSizeChunker` размер фрагмента по умолчанию составляет **500 символов** (`chunkSize: Int = 500`). Источник: `FixedSizeChunker.kt`, раздел `FixedSizeChunker`."

**Анализ:** Модель галлюцинировала типичное значение (512 токенов), тогда как реальное — 500 *символов* (не токенов). RAG дал точный ответ из кода.

---

### Вопрос 2: Процент перекрытия в FixedSizeChunker

**Ответ без RAG:**
> "Стандартный процент перекрытия (overlap) обычно составляет 10-20%. Распространённое значение — 10% или 20%, в зависимости от выбора разработчика."

**Ответ с RAG:**
> "По умолчанию используется `overlapPct: Float = 0.12f` — то есть **12%**. При chunkSize=500 это составляет ~60 символов перекрытия. Источник: `FixedSizeChunker.kt`."

**Анализ:** Без RAG — типичный диапазон (правильный по смыслу, но неверный конкретный). С RAG — точное значение из кода.

**Ответ с RAG:**

**Анализ:** Модель назвала правильную размерность (1536), но ошибилась с названием модели (ada-002 вместо text-embedding-3-small). RAG указал точное название.

### Вопрос 5: Формат хранения векторов в SQLite

**Ответ без RAG:**
> "Векторы обычно хранятся в бинарном формате BLOB или как JSON-массив чисел. Некоторые реализации используют специализированные расширения SQLite для векторного поиска."

**Ответ с RAG:**
> "Векторы хранятся как **Base64-кодированные байты IEEE 754 float** в TEXT-колонке таблицы `embeddings`. При записи: `ByteBuffer.allocate(size * 4)` → float → Base64. При чтении: Base64 → bytes → ByteBuffer → FloatArray. Источник: `SqliteVectorStore.kt`."

**Анализ:** Без RAG — правдоподобные, но ложные предположения (BLOB/JSON). С RAG — точное описание алгоритма из кода.

### Вопрос 6: Максимальный параллелизм в IndexPipeline

**Ответ без RAG:**
> "Параллелизм при генерации эмбеддингов зависит от реализации. Обычно используют coroutine pool с размером, равным количеству ядер процессора или фиксированным значением вроде 10-20."

**Ответ с RAG:**
> "Максимальный параллелизм ограничен **5 одновременными запросами** через `Semaphore(maxConcurrentEmbeddings)`, где `maxConcurrentEmbeddings = 5` — параметр конструктора `IndexPipeline`. Источник: `IndexPipeline.kt`."

**Анализ:** Модель угадала диапазон (10-20), но конкретное значение (5) знает только RAG.

## 6. Выводы

### Когда RAG особенно важен

1. **Проект-специфичные факты** — константы, пути, имена классов, конфигурации
2. **Технический долг и архитектурные решения** — "почему выбран именно этот подход"
3. **Актуальность** — документация может устареть, код — нет

### Ограничения текущей реализации

- **Brute-force поиск** — `SqliteVectorStore.search()` загружает *все* векторы в память. При >100K фрагментах потребуется HNSW или pgvector
- **Одна embedding-модель** — при индексации и поиске должна использоваться одна и та же модель (text-embedding-3-small)
- **Статичный индекс** — изменения в файлах не отражаются автоматически, нужно переиндексировать

### Следующие шаги (вне scope этой задачи)

- Гибридный поиск: BM25 (keyword) + vector similarity
- Метаданная фильтрация: поиск только в `.kt` файлах или только в `README.md`
- Переранжирование (re-ranking) через cross-encoder
