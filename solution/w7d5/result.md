# AI-Driven Quality Gate: Кейс-стади по внедрению автоматического ревьюера Pull Request

**Продукт:** LLM Chat CLI Agent  
**Стек:** Kotlin · Koog · RAG · GitHub Actions  

---

## 1. Проблема: Узкое горлышко ручного ревью

Ручной Code Review — один из главных факторов, замедляющих итерационный цикл разработки. В типичной команде:

- **Задержка обратной связи** составляет от нескольких часов до нескольких дней — разработчик к тому моменту уже переключился на другой контекст
- **Неравномерность покрытия**: ревьюеры концентрируются на знакомых участках кода, системные проблемы и нарушения архитектурных инвариантов остаются незамеченными
- **Накопление технического долга**: архитектурные отклонения, которые можно исправить на стадии PR, превращаются в рефакторинг через полгода
- **Несоответствие кода и документации**: diff не содержит контекст проекта. Ревьюер-человек вынужден держать в голове всю архитектуру; статические линтеры (ktlint, detekt) работают только с синтаксисом и стилем — они слепы к семантике и не понимают намерений кода

Ни один из существующих инструментов не решает задачу **контекстно-осведомлённого семантического анализа** — ревью с пониманием того, как изменение вписывается в архитектуру конкретного проекта.

---

## 2. Решение: Context-Aware AI Quality Gate

### Ключевая идея

AI-ревьюер — это не замена линтеру и не замена человеку. Это **третий слой качества**, который заполняет пробел между синтаксическими проверками и финальным решением человека:

```
PR → ktlint / detekt          ← блокирует нарушения стиля и безопасности (детерминировано)
   → AI Quality Gate           ← семантический анализ с контекстом проекта (не блокирует)
   → Human Reviewer            ← финальное архитектурное решение
```

### Архитектура: "Deep Review" через RAG + LLM

Система состоит из трёх компонентов, каждый из которых решает конкретную проблему:

```
GitHub PR (opened / synchronize)
         │
         ▼
GitHub Actions: ai-review.yml
         │
         ├── Build shadow JAR (Kotlin → JVM)
         │
         ├── RAG Cache (key: hashFiles('**/*.kt', '**/*.md', '**/*.txt'))
         │       ├── HIT  → ~/.llmchat/knowledge-base.db восстановлен из кэша
         │       └── MISS → --build-index . (индексация кодовой базы в SQLite)
         │
         ├── gh pr diff → /tmp/pr-diff.patch
         │
         └── java -jar cli-app-all.jar
                 --headless           ← без интерактивного терминала
                 --diff-file patch    ← изменения PR
                 --rag                ← включить RAG-контекст
                 --temperature 0.1    ← воспроизводимость результата
                 │
                 ├── RagService.augment(diff)
                 │       └── cosine similarity → топ-K релевантных фрагментов кодовой базы
                 │
                 ├── ConversationManager.sendMessage(diff + ragContext)
                 │       └── LLM (один вызов, structured output)
                 │
                 └── stdout → /tmp/review-output.md
                         └── gh pr comment → публикация в PR
```

**Почему RAG меняет качество ревью принципиально:**

| Без RAG (базовый LLM)                    | С RAG (Context-Aware)                                                 |
|------------------------------------------|-----------------------------------------------------------------------|
| Видит только изменённые строки           | Видит diff + релевантный контекст существующего кода                  |
| Не знает архитектурных паттернов проекта | Знает: `SlidingWindowStrategy`, `ContextStrategy`, `InvariantStorage` |
| Высокий процент ложных срабатываний      | Снижение false positives — агент видит «правильные» паттерны проекта  |
| Не видит смежные модули                  | Замечает нарушение контрактов между модулями                          |

**Почему Headless mode + CI/CD — это Seamless Integration:**

Агент запускается как обычный Unix-процесс: `stdin/stdout/stderr`, exit code. Никаких интерактивных компонентов, никакого JLine/Mordant в headless-режиме. Это означает полную совместимость с любой CI-платформой без каких-либо специальных адаптеров.

**🟠 High Priority:** None identified.  
**🟡 Medium Priority — Реальная находка:**

> **Файл:** `cli-app/src/main/kotlin/llmchat/Main.kt`, строки 85–89  
> *"Функция `startInteractiveCli` вызывается без проверки `apiKey` на `null`, когда `headlessMode = false`. Потенциальный `NullPointerException` в runtime."*  
> **Рекомендация:** добавить null-проверку перед вызовом функции.

**💡 Suggestions (архитектурный уровень):**
1. `CliConfig.kt:24-30` — использовать sealed classes вместо множественных nullable параметров для типобезопасности
2. `CliOutput.kt:220-226` — `printPlain` как extension function на `PrintStream` для идиоматичного Kotlin
3. `Main.kt:863-867` — sealed classes или `Result<T>` вместо прямых `System.err.println` для централизованной обработки ошибок

**Что это демонстрирует:** агент не просто проверяет стиль — он выявляет **потенциальный runtime-дефект** (NPE), который линтер не нашёл бы, и предлагает **архитектурные улучшения** с конкретными ссылками на файлы и строки.

## 4. Value Proposition: Масштабирование экспертизы

### Немедленный feedback loop

Традиционный ревью: разработчик ждёт часы или дни. AI Quality Gate: **4 минуты после открытия PR**. Для маленьких итерационных изменений это означает возможность исправить проблему до того, как переключился на следующую задачу — пока контекст ещё в оперативной памяти.

### Консистентность, независимая от нагрузки команды

Человек-ревьюер в конце рабочего дня пропускает очевидные вещи. AI Quality Gate выполняет анализ с одинаковой глубиной в 23:00 в пятницу и в понедельник утром. Это особенно критично для проверки **архитектурных инвариантов** — правил, которые легко нарушить случайно, но сложно заметить при поверхностном просмотре.

### Сохранение экспертизы в RAG

RAG-индекс — это **«знания проекта», закодированные в векторах**. Когда опытный разработчик покидает команду, его архитектурные решения остаются в кодовой базе и продолжают влиять на качество ревью. Новый человек в команде получает AI-ревьюера, который уже знает паттерны проекта.

### Дифференциация от статического анализа

| Критерий                           | ktlint/detekt | AI Quality Gate |
|------------------------------------|---------------|-----------------|
| Нарушения стиля                    | ✅             | ✅               |
| Потенциальные NPE / runtime-ошибки | ⚠️ частично   | ✅               |
| Архитектурные паттерны проекта     | ❌             | ✅ (через RAG)   |
| Нарушения межмодульных контрактов  | ❌             | ✅               |
| Понимание намерений кода           | ❌             | ✅               |
| Человекочитаемые объяснения        | ❌             | ✅               |

## 5. Технические решения, обеспечивающие Production Readiness

### Воспроизводимость: temperature = 0.1

LLM по умолчанию — стохастический инструмент. Фиксация `--temperature 0.1` делает ревью **квазидетерминированным**: один и тот же diff дважды подряд даёт практически идентичный результат. Это критично для аудита и сравнения ревью разных версий PR.

### Умное кэширование RAG-индекса

```yaml
key: rag-index-${{ hashFiles('**/*.kt', '**/*.md', '**/*.txt') }}
```

Индекс перестраивается только при реальном изменении исходных файлов. Cache HIT = мгновенный старт ревью без затрат на переиндексацию. Это снижает latency и стоимость при высокой частоте PR.

### Изоляция процесса: stderr/stdout разделение

```bash
java -jar cli-app-all.jar \
  2>/tmp/review-stderr.log \
  > /tmp/review-output.md
```

Отладочные логи (stderr) никогда не попадают в PR-комментарий. В GitHub Actions они доступны для диагностики, но конечный пользователь видит только чистый Markdown-отчёт.

### Артефакты для аудита

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: ai-review-${{ github.event.pull_request.number }}
    path: /tmp/review-output.md
    retention-days: 30
```

Каждый ревью сохраняется как GitHub Artifact на 30 дней — полная трассируемость, кто что получил и когда.

## 6. Roadmap: От Quality Gate к Automated DevEx

Текущая реализация — это **Фаза 1: Automated Feedback**. Архитектура намеренно заложена с расчётом на расширение:

### Фаза 2: Automatic Remediation (следующий шаг)

AI находит NPE → AI генерирует патч → патч предлагается как suggested change прямо в PR интерфейсе GitHub. Разработчик нажимает «Apply suggestion» — исправление сделано без переключения контекста.

**Техническая основа:** агент с file tools (уже реализован в W7D4) + `gh pr review --comment` с `--body` содержащим `suggestion` блок.

### Фаза 3: Cross-Service Impact Analysis

В микросервисной архитектуре изменение одного сервиса ломает контракты смежных. RAG-индекс расширяется до **federation**: каждый сервис индексирует свои API-контракты (OpenAPI, Protobuf). При ревью агент проверяет, не нарушает ли diff публичные контракты, которые используют другие сервисы.

### Фаза 4: Automatic Documentation Update

RAG обнаруживает несоответствие между кодом и документацией → агент предлагает обновление `README.md` / `CLAUDE.md` / OpenAPI схемы как отдельный коммит в PR. Документация перестаёт устаревать.

### Фаза 5: Invariant Enforcement

Архитектурные инварианты (система уже реализована в `agent/invariant/`) становятся частью ревью: нарушение инварианта `STACK` или `ARCHITECTURE` превращается в **blocking check** наравне с ktlint. Архитектурные решения, принятые командой, автоматически соблюдаются на уровне CI.

## Итог

AI Quality Gate — это **работающий инструмент**, который:

1. **Уже интегрирован** в реальный CI/CD pipeline (`ai-review.yml`)
2. **Уже нашёл** реальный дефект в реальном PR (потенциальный NPE, [PR #1](https://github.com/dalapenko/simple-llm-sample/pull/1#issuecomment-4164616166))
3. **Работает за 4 минуты** — быстрее любого человека-ревьюера
4. **Масштабируется** на любое количество PR без увеличения нагрузки на команду
5. **Дифференцирован от линтеров** за счёт контекстно-осведомлённого анализа через RAG

Комбинация Kotlin + Koog + RAG + GitHub Actions создаёт систему, которая сегодня ускоряет feedback loop, а завтра — при минимальных доработках — закрывает полный цикл от обнаружения дефекта до его исправления без участия человека.
