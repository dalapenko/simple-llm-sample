# Задание W7D3 — User Support Assistant (MCP + RAG)

## Что реализовано

Добавлен режим `support` в существующий Kotlin CLI-агент на базе Koog.  
Команда запуска:

```
java -jar cli-app-all.jar support --ticket-id TKT-201
```

Агент за один ход:
1. Поднимает MCP-сервер (`mcp-server-support`) как дочерний процесс через stdio.
2. Индексирует FAQ-документацию (`docs/support-faq/auth-faq.md`) в отдельную RAG-базу `~/.llmchat/support-data/support-knowledge.db`.
3. Инструктируется обязательно вызвать `get_ticket_context` перед ответом.
4. Получает данные пользователя из CRM через MCP-инструмент.
5. Обогащает запрос релевантными фрагментами FAQ через RAG.
6. Формирует эмпатичный ответ на русском языке.

---

## Как работает пайплайн

```
Пользователь (CLI) → SupportRunner
   │
   ├── RAG: индексация docs/support-faq/ → support-knowledge.db
   │         → augment("authorization failure suspended locked 403")
   │
   ├── MCP: java -jar mcp-server-support.jar <data-path>   (subprocess, stdio)
   │         tools: get_ticket_context(ticket_id)
   │                list_user_tickets(user_identifier)
   │
   └── AIAgent (Koog, chatSingleRunGraphStrategy)
         system: SUPPORT_SYSTEM_PROMPT (эмпатия, русский, обязательный вызов MCP)
         user:   "Вызови get_ticket_context для TKT-201, ответь на вопрос..."
                 + RAG-фрагменты из FAQ
         → LLM вызывает get_ticket_context → получает статус suspended + overdue
         → формирует персонализированный ответ для Дмитрия Козлова
```

---

## Демонстрационный сценарий (TKT-201)

**Пользователь:** Дмитрий Козлов, план enterprise, статус `suspended`, просроченный платёж.  
**Запрос:** "Почему не работает авторизация?"

**Что произошло:**
- MCP вернул: `account_status: suspended`, `payment_status: overdue`, `plan: enterprise`
- RAG нашёл 5 фрагментов: причины 403, заблокированный аккаунт, приостановленный аккаунт
- Агент обратился по имени, объяснил причину (`suspended` из-за overdue), дал пошаговые инструкции
- Ответил на русском, не пытался разблокировать (корректная эскалация в Биллинг)

---

## Почему --ticket-id полезен

Флаг `--ticket-id` решает задачу **детерминированной персонализации**.

Без него агент не знает, о каком пользователе идёт речь: можно спросить текст вопроса,
но MCP-инструмент `get_ticket_context` требует конкретный ID.  
С флагом:
- агент сразу получает якорь для инструментального вызова,
- данные из CRM загружаются **до** формирования ответа,
- ответ строится на реальном контексте (статус, план, история), а не на предположениях.

Альтернатива — попросить LLM самостоятельно спросить у пользователя ID — добавляет
лишний ход и ухудшает UX в CLI-сценариях.

## Агентный подход: достоинства и ограничения

### Достоинства по сравнению с классическим чат-ботом

| Аспект         | Классический чат-бот      | Агент (MCP + RAG)                                |
|----------------|---------------------------|--------------------------------------------------|
| Персонализация | Вручную прописанные ветки | Автоматически через CRM-данные                   |
| Знания         | Статичный скрипт          | Живой FAQ (RAG), обновляется без перекодирования |
| Эскалация      | Хардкод условий           | Системный промпт + статус из CRM                 |
| Расширяемость  | Переписать скрипт         | Добавить новый MCP-инструмент                    |

### Ограничения и риски

- **Латентность**: каждый ответ = 1–2 сетевых вызова (LLM) + запуск subprocess (MCP).  
  Для высоконагруженного saas неприемлемо без кеширования.
- **Стоимость**: RAG-embeddings + LLM-вызов дороже детерминированного дерева решений.
- **Непредсказуемость**: LLM может отклониться от системного промпта.  
  Обязательные вызовы инструментов нельзя гарантировать без structured outputs / forced tool use.
- **PII**: данные пользователя проходят через LLM-провайдер — необходима оценка compliance.
- **Отладка**: сложнее воспроизвести баг, чем в детерминированном скрипте.
