# W5D5 — Production-Ready RAG Chat с диалоговой памятью и состоянием задачи

---

## 1. Что реализовано

### Новые компоненты

| Файл                           | Назначение                                                                            |
|--------------------------------|---------------------------------------------------------------------------------------|
| `HistoryAwareQueryRewriter.kt` | Контекстуальное переписывание запроса с учётом истории диалога                        |
| `TaskStateManager.kt`          | Тихое извлечение и обновление состояния задачи (цель, ограничения, термины, знания)   |
| `ConversationalRagService.kt`  | Обёртка над `AdvancedRagService` с двухстадийным переписыванием и инъекцией состояния |

### Изменения в существующих файлах

- `RagMode.kt` — добавлен режим `conversational`
- `Commands.kt` — добавлены команды `/reset` и `/state`
- `ConversationManager.kt` — добавлен метод `setRagTaskStateBlock()` для инъекции состояния в системный промпт
- `Main.kt` — подключение нового режима, обновление истории и задачи после каждого хода

### Полный пайплайн в режиме `conversational`

```
raw query
  → HistoryAwareQueryRewriter  (разрешает местоимения, использует последние N ходов + TaskState)
  → standalone query
  → AdvancedRagService          (HyDE расширение → embed → поиск → фильтрация → LLM rerank)
  → RAG промпт + блок TaskState
  → LLM ответ
  → [тихо] TaskStateManager.updateFromTurn()  (обновляет цель/ограничения/термины/знания)
  → ConversationManager.setRagTaskStateBlock() (обновляет системный промпт на следующий ход)
```

## 4. Анализ дрейфа контекста (Context Drift)

### Наблюдения

**Без TaskState (гипотетический сценарий):**
- При скользящем окне в 10 сообщений, к ходу 12 ограничения с хода 4 были бы вытеснены
- На ходу 14 агент мог бы написать код с прямыми `launch {}` вместо Koog-обёртки
- Цель "онбординг" была бы "забыта" — ответы стали бы общими

**С TaskState:**
- Ограничения сжаты в ~200 токенов и инжектируются в **системный промпт** (не в историю)
- Системный промпт сохраняется при каждом ходу независимо от размера истории
- Проверка на ходу 15: все 3 ограничения воспроизведены точно

### Качество источников

В обоих сценариях каждый ответ с фактическими утверждениями содержал:
- `## Источники` — список с ID фрагментов в формате `[ID: xxxxxxxx] filename (section)` на **русском языке**
- `## Цитаты` — дословные цитаты из индексированных документов на **русском языке**

Ни в одном ходу агент не дал фактического утверждения без источника.

## 5. Технические решения

### Двухстадийное переписывание запроса

```
ход 9: "Почему поиск не возвращает ничего? Что может быть не так?"
  → HistoryAwareQueryRewriter:
    "PDF-файлы не индексируются в SqliteVectorStore — возможные причины ошибки в IndexPipeline,
     PdfExtractor или similarityThreshold"
  → QueryRewriter (HyDE):
    "Apache PDFBox PdfExtractor sortByPosition IndexPipeline error empty results SqliteVectorStore
     search cosine similarity threshold 0.65 FilteredChunks VectorStore.search()"
  → [поиск по векторной БД с оптимальным запросом]
```

### TaskState и токены

| Компонент                          | Токены     |
|------------------------------------|------------|
| Скользящее окно истории (10 ходов) | ~2000–4000 |
| TaskState в системном промпте      | ~150–300   |
| RAG контекст (3 фрагмента)         | ~600–1200  |

TaskState даёт максимальную информацию при минимальных токенах: 150–300 токенов против 2000–4000 полной истории.
