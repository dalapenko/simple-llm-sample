# Индексирование документов — векторная база знаний для RAG

## Что сделано

Реализован новый Gradle-модуль `:indexer`, который превращает локальные файлы в базу знаний с векторным поиском. Модуль подключён к `cli-app` через команду `/index`. Достаточно указать папку — и все документы будут разбиты на смысловые фрагменты, превращены в векторные эмбеддинги и сохранены в SQLite. Это фундамент для RAG (Retrieval-Augmented Generation): впоследствии CLI сможет искать релевантные фрагменты и подставлять их в контекст к LLM.

---

## Зачем это нужно

Когда у LLM нет доступа к конкретным документам проекта, он отвечает из общих знаний. Индексирование решает эту проблему:

- **Приватные документы.** Внутренняя документация, README, спецификации, архитектурные решения — всё это можно добавить в базу, не отправляя в интернет.
- **Актуальность.** В отличие от дообучения, база знаний обновляется за секунды: переиндексируйте папку после любых изменений.
- **Масштаб.** Даже тысячи документов хранятся локально в одном SQLite-файле — никаких внешних сервисов не нужно.
- **Ответы по коду.** Kotlin-файлы проекта можно проиндексировать так же, как и markdown-документацию, и потом задавать вопросы о конкретных функциях или классах.

## Как это работает

```
  Файлы на диске
  (.md, .kt, .txt, .py, .pdf)
         │
         ▼
  DocumentLoader — обходит директорию рекурсивно
         │
         ▼
  Chunker — разбивает каждый документ на фрагменты
  │
  ├─ StructuralChunker — по заголовкам и объявлениям
  │    .md → по заголовкам (#, ##, ###)
  │    .kt → по top-level объявлениям (class, fun, object)
  │    остальное → по абзацам (двойной перевод строки)
  │
  └─ FixedSizeChunker — скользящее окно, 500 символов, 12% перекрытие
         │
         ▼
  EmbeddingClient — текст каждого фрагмента → вектор из 1536 чисел
  (OpenRouter, модель text-embedding-3-small)
         │
         ▼
  SqliteVectorStore — сохраняет фрагмент + вектор в ~/.llmchat/knowledge-base.db
```

Индексирование ведётся параллельно: до 5 запросов к API одновременно (ограничение через `Semaphore`). Чанки хранятся с метаданными: путь к файлу, заголовок документа, название секции, стратегия разбиения.

---

## Две стратегии разбиения

| Стратегия       | Принцип                                         | Плюсы                                        |
|-----------------|-------------------------------------------------|----------------------------------------------|
| `structural`    | По структуре документа (заголовки, объявления)  | Каждый чанк — цельная смысловая единица      |
| `fixed`         | Окно фиксированного размера с перекрытием       | Равномерное покрытие, предсказуемый размер   |

`structural` подходит для хорошо структурированных документов (код, markdown с заголовками). `fixed` — надёжный fallback для любых текстов.

## Руководство по использованию

### Сборка

```bash
./gradlew :cli-app:shadowJar
```

### Запуск CLI

```bash
./gradlew :cli-app:run --console=plain
# или
./start.sh
```

### Команды индексирования

```
/index ./docs                          — индексировать с structural-стратегией (по умолчанию)
/index ./docs fixed                    — индексировать с fixed-стратегией
/index ./docs structural --report      — индексировать и показать сравнение стратегий
/index ./solution structural --report  — пример: проиндексировать папку solution/
```

Флаг `--report` запускает обе стратегии и выводит сравнительную таблицу: количество чанков, средний размер, доля чанков с метаданными секции. API-запросы делаются только для основной стратегии — альтернативная считается локально.

### База знаний

Все данные хранятся в:
```
~/.llmchat/knowledge-base.db
```

## Что произошло в демо

**Сессия записана в [`indexer.cast`](../../internal/w5d1/indexer.cast)**

```
[Пользователь]  Хочу проиндексировать документы проекта

[AI]  Конечно! Используйте команду /index:
      /index ./solution                   — структурное разбиение (по умолчанию)
      /index ./solution fixed             — фиксированный размер чанков
      /index ./solution structural --report — сравнение двух стратегий

[Пользователь]  /index ./solution structural --report

  ⠋ Indexing ./solution [structural]...  0s
  ⠙ Indexing ./solution [structural]...  1s
  ...
  ⠏ Indexing ./solution [structural]...  5s

 Index complete
  Directory : ./solution
  Files     : 19
  Time      : 43 218 ms

  Strategy Comparison:
  Strategy           Chunks  Avg size (chars)   Metadata density
  --------------------------------------------------------------
  structural             332            463,5            100,0%
  fixed                  360            482,2            100,0%

  Index stored at ~/.llmchat/knowledge-base.db

[Пользователь]  /exit

Goodbye!
```

Оба метода дали 100% покрытие метаданными — FixedSizeChunker тоже проставляет номер секции (`chunk-1`, `chunk-2`, ...), поэтому поле `section` никогда не бывает null. Structural создала 332 чанка против 360 у fixed при чуть большем среднем размере (463 vs 482 символов) — это ожидаемо: структурные границы дают более длинные, но смысловые фрагменты.
