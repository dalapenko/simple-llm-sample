# AI-ревьюер Pull Request на базе LLM-агента

## Что реализовано

Добавлен автоматический ревьюер PR, состоящий из трёх частей:

1. **Headless-режим CLI** (`--headless`) — Kotlin-агент запускается без интерактивного терминала, принимает git diff через файл (`--diff-file`) или stdin, выполняет один LLM-вызов и выводит результат в stdout.
2. **GitHub Actions workflow** (`.github/workflows/ai-review.yml`) — оркестратор, который запускается на каждый PR, строит индекс RAG, передаёт diff агенту и публикует ревью комментарием к PR.
3. **Опциональное построение RAG-индекса** (`--build-index`) — прямо в headless-режиме, без JLine и терминала.

---

## Архитектура: общий workflow

```
GitHub PR (opened / synchronize)
        │
        ▼
GitHub Actions: ai-review.yml
        │
        ├── actions/checkout (fetch-depth: 0)
        ├── setup-java 21 + Gradle build → cli-app-all.jar
        │
        ├── actions/cache (key: hash *.kt + *.md)
        │       ├── cache HIT  → ~/.llmchat/knowledge-base.db восстановлен
        │       └── cache MISS → передаём --build-index . агенту
        │
        ├── gh pr diff → /tmp/pr-diff.patch
        │
        ├── java -jar cli-app-all.jar
        │       --headless
        │       --diff-file /tmp/pr-diff.patch
        │       --rag
        │       [--build-index .  ← только при cache MISS]
        │       2>/tmp/stderr.log   stdout>/tmp/review-output.md
        │
        │   Внутри агента:
        │       ├── [опц.] IndexPipeline.run() → SQLite ~/.llmchat/knowledge-base.db
        │       ├── RagService.create() → загрузка векторного индекса
        │       ├── ragService.augment(diff) → поиск релевантных фрагментов кода
        │       ├── ConversationManager.sendMessage(augmentedMessage)
        │       │       └── AIAgent → LLM (один вызов, temperature=0.1)
        │       └── println(response) → stdout (plain text, без ANSI)
        │
        └── gh pr comment → публикация Markdown-ревью в PR
```

## System prompt для ревью

В headless-режиме агент получает специализированный системный промпт (если пользователь не передал `--system-prompt`):

- Роль: "эксперт по Kotlin, выполняющий ревью PR"
- Формат вывода: пять секций Markdown — Critical / High / Medium / Suggestions / Summary
- Акцент: только реальные проблемы и конкретные исправления, без пересказа того, что делает код
- Если в категории нет замечаний — явно написать «None identified»

Для воспроизводимости ревью температура зафиксирована на `0.1`.

## Как RAG повышает точность ревью

Без RAG агент видит только изменённые строки и не понимает контекст проекта. С RAG:

- **Проверка архитектурной согласованности**: индекс содержит существующий исходный код. Агент видит, какие паттерны уже используются (`SlidingWindowStrategy`, `ContextStrategy`, `AgentFactory`), и замечает отклонения в новом коде.
- **Связный контекст модулей**: изменение в одном модуле может нарушить контракт другого. RAG позволяет агенту увидеть смежный код, который не попал в diff.
- **Проверка инвариантов**: если в знаниях базы есть документация или CLAUDE.md с ограничениями стека, агент может выявить нарушения (например, использование неодобренной библиотеки).
- **Снижение ложных срабатываний**: зная реальный код вокруг изменений, агент меньше придирается к «правильным» паттернам, которые уже применяются в проекте.

RAG-индекс кешируется в GitHub Actions по хэшу исходных файлов — перестройка происходит только при реальных изменениях кодовой базы.

## Плюсы и минусы AI-ревью по сравнению с традиционными линтерами

### Плюсы AI-ревьюера

| Аспект                      | Описание                                                                                    |
|-----------------------------|---------------------------------------------------------------------------------------------|
| **Семантическое понимание** | Линтер проверяет синтаксис и стиль; LLM понимает намерение кода и находит логические ошибки |
| **Контекст проекта**        | RAG позволяет агенту учитывать специфику именно этого проекта, а не абстрактные правила     |
| **Гибкость**                | Нет нужды писать правила для каждого нового паттерна — агент обобщает сам                   |
| **Архитектурные замечания** | Линтер не скажет «этот класс нарушает принцип единственной ответственности»; LLM — может    |
| **Естественный язык**       | Ревью читается как комментарий коллеги, а не как набор кодов ошибок                         |

### Минусы AI-ревьюера

| Аспект                            | Описание                                                                               |
|-----------------------------------|----------------------------------------------------------------------------------------|
| **Не детерминирован**             | Один и тот же diff может получить разные ревью при разных запусках                     |
| **Галлюцинации**                  | Агент может указать на «проблему», которой не существует, или предложить нерабочий fix |
| **Ограничение контекстного окна** | Большие PR (>30 000 символов diff) обрезаются; часть кода не анализируется             |
| **Стоимость**                     | Каждый вызов тратит токены и деньги; при высокой частоте PR затраты растут             |
| **Нет строгих гарантий**          | Линтер всегда блокирует конкретное нарушение; LLM может пропустить очевидную проблему  |
| **Латентность**                   | LLM-вызов занимает 10–60 секунд, тогда как линтер — секунды                            |

### Рекомендация

AI-ревьюер и линтеры — взаимодополняющие инструменты, а не конкуренты. Оптимальная схема:

```
PR → линтер (ktlint, detekt) → блокирует нарушения стиля/безопасности
   → AI-ревьюер              → добавляет семантические комментарии (не блокирует)
   → человек-ревьюер         → финальное решение
```
