# W6D4 — Оптимизация локального LLM под конкретную задачу

---

## 1. Зачем это нужно

Когда вы запускаете локальную модель с настройками по умолчанию, она ведёт себя как универсальный ассистент — отвечает на вопросы о погоде, объясняет математику, пишет стихи. Такой режим намеренно сделан «средним»: подходит для всего, но не оптимален ни для чего конкретного.

Если вы точно знаете, для чего используете модель — например, только для код-ревью — можно настроить её поведение так, чтобы она работала значительно лучше именно в этой задаче. Не потому что сама модель стала умнее, а потому что вы убрали всё лишнее и сфокусировали её внимание.

---

## 2. Что меняется на практике

Демо `solution/w6d4/demo.gif` показывает один и тот же запрос к двум конфигурациям — базовой и оптимизированной под код-ревью.

### Базовая конфигурация (без настройки)

Ответ приходит в виде свободного текста: «во-первых... во-вторых... в целом рекомендуется...». Модель сама решает, что важно, а что нет. Проблемы упоминаются в произвольном порядке, без оценки серьёзности. Из-за высокой температуры (случайности) один и тот же запрос в разные дни может дать заметно разные ответы.

### Оптимизированная конфигурация (пресет `code-review`)

Ответ структурирован по уровням серьёзности: **Critical → High → Medium → Low**. Каждая проблема содержит конкретное описание и готовый исправленный код. Критическая уязвимость (SQL-инъекция) выделяется первой — её нельзя пропустить. Ответ воспроизводимый: при повторном запросе структура и выводы остаются теми же.

### Сравнение

| Параметр                | Базовая конфигурация                   | Пресет `code-review`              |
|-------------------------|----------------------------------------|-----------------------------------|
| Модель                  | `llama3.2` (общего назначения)         | `qwen2.5-coder:7b-q4_K_M` (код)   |
| Температура             | 1.0 — творческий режим                 | 0.1 — почти детерминированный     |
| Структура ответа        | Произвольный текст                     | Critical / High / Medium / Low    |
| Воспроизводимость       | Ответы отличаются от запроса к запросу | Стабильный результат              |
| Пропуск серьёзных багов | Возможен — тон одинаковый для всего    | Маловероятен — критичное выделено |

## 3. Плюсы и минусы оптимизации

### Плюсы

- **Структура вместо потока сознания.** Модель, которой сказано «выдавай только Critical / High / Medium», не будет смешивать опечатку с SQL-инъекцией в одном абзаце. Вы сразу видите, что критично, а что можно исправить потом.
- **Стабильность.** Низкая температура означает, что модель выбирает наиболее очевидный ответ, а не случайный. Для проверки кода это важно: хочется, чтобы уязвимость была найдена каждый раз, а не в 70% случаев.
- **Специализированная модель понимает код лучше.** `qwen2.5-coder` обучена на кодовых репозиториях — она точнее распознаёт паттерны ошибок, знает стандартные anti-patterns и типичные уязвимости.
- **Ограничение объёма.** Настроенный лимит токенов не даёт модели писать «воду». Ответ содержит только находки, без предисловий и заключений.

### Минусы

- **Пресет заточен под одну задачу.** Конфигурация для код-ревью даст плохой результат, если задать ей бытовой вопрос или попросить написать текст: температура 0.1 делает ответы сухими и лишёнными вариативности.
- **Нужно скачать дополнительную модель.** `qwen2.5-coder:7b-q4_K_M` — около 5 ГБ. Если её нет локально, Ollama выдаст ошибку при запуске.
- **Качество ограничено железом.** Даже оптимизированная конфигурация упирается в возможности компьютера: 7B-модель на машине без GPU работает заметно медленнее облачного API.

### Когда оптимизация оправдана

| Ситуация                                    | Рекомендация         |
|---------------------------------------------|----------------------|
| Регулярно делаете одного и то же            | Пресет               |
| Нужны стабильные, воспроизводимые ответы    | Пресет               |
| Разговариваете с ассистентом на разные темы | Базовая конфигурация |
| Нет нужной модели или мало RAM              | Базовая конфигурация |
| Хотите проверить одну функцию «на лету»     | Базовая конфигурация |

## 4. Как запустить

### Установить модель для пресета

```bash
# Скачать специализированную модель (~5 ГБ, нужна один раз)
ollama pull qwen2.5-coder:7b-q4_K_M

# Убедиться что Ollama запущена
ollama serve
```

### Базовый запуск (без оптимизации)

```bash
./gradlew :cli-app:run --console=plain \
  --args="--provider ollama --local-model llama3.2"
```

### Запуск с пресетом code-review

```bash
./gradlew :cli-app:run --console=plain \
  --args="--provider ollama --preset code-review"
```

### Переопределить отдельный параметр пресета

```bash
# Взять пресет, но поменять модель (например, если нет qwen2.5-coder)
./gradlew :cli-app:run --console=plain \
  --args="--provider ollama --preset code-review --local-model codellama:7b"
```

## 5. Важные детали

- **Пресет — это набор умолчаний, не жёсткий режим.** Любой параметр пресета можно переопределить флагом командной строки. Флаги всегда имеют приоритет.
- **Температура влияет на весь диалог.** При `temp=0.1` модель будет лаконична и предсказуема во всех ответах — не только в код-ревью. Если в рамках той же сессии захотите попросить объяснение концепции, ответ тоже будет сухим.
- **Встроенный пресет `baseline`** запускает базовые настройки явно — удобно для честного сравнения результатов в одной команде.
- **Собственные пресеты** можно положить в файл `presets/<имя>.json` рядом с проектом и подключить через `--preset <имя>`.
