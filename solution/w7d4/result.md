# W7D4 — Active Project File Assistant

---

## Принципы работы

Агент получает от пользователя высокоуровневую цель на естественном языке и самостоятельно решает, какие инструменты вызвать для её достижения. Файловые операции реализованы как набор инструментов. Каждый инструмент описывает свои параметры и назначение так, чтобы языковая модель могла выбрать подходящий в зависимости от контекста.

В system prompt агента добавлен специальный блок `[FILE TOOLS AVAILABLE]`, который перечисляет доступные инструменты: `search_files`, `read_file`, `write_file`, `list_files`, `run_build_check`. Благодаря этому модель с самого начала знает о своих возможностях и не пытается галлюцинировать несуществующие операции.

Цикл выполнения выглядит следующим образом: модель получает запрос, формирует список вызовов инструментов, Koog выполняет их последовательно или параллельно, результаты возвращаются в контекст, и модель продолжает рассуждение до формирования финального ответа пользователю.

## Преимущества прямого доступа к файлам

**Автономное выполнение сложных задач.** Пользователь формулирует цель одним сообщением — агент сам строит цепочку действий: поиск → чтение → анализ → запись результата. Никакого ручного копирования файлов или промежуточных шагов не требуется.

**Работа с несколькими файлами в одном диалоге.** Агент может за одну сессию найти все упоминания класса в 20 файлах, прочитать каждый, сопоставить данные и сформировать сводный отчёт. Без файлового доступа пользователю пришлось бы вручную передавать содержимое каждого файла.

**Self-verification через `run_build_check`.** После внесения изменений агент может запустить компиляцию и убедиться, что его правки не сломали проект. Это делает цикл редактирования замкнутым: агент видит последствия своих действий и может их скорректировать до того, как передаст управление пользователю.

## Недостатки и риски

**Path traversal атаки.** Если не ограничить разрешённые пути, языковая модель (или внешний злоумышленник через prompt injection) может попытаться прочитать или перезаписать файлы за пределами рабочей директории — например, `../../.ssh/id_rsa`. Решение: canonical path sandbox, который проверяет, что итоговый путь начинается с разрешённой базовой директории.

**Случайная перезапись важных файлов.** Агент может переписать `build.gradle.kts` или другой критичный файл, если пользователь неточно сформулировал задачу. Решение: atomic writes (запись во временный файл с последующим переименованием) и sandbox, ограничивающий запись определёнными директориями.

**Неограниченный доступ требует доверия к LLM.** В отличие от инструментов с чётко фиксированным поведением, файловый агент действует по своему усмотрению. Качество и безопасность результата напрямую зависят от того, насколько точно языковая модель интерпретирует намерения пользователя.

**Непредсказуемость выбора файлов.** Трудно заранее сказать, какие именно файлы агент решит прочитать или изменить в ответ на конкретный запрос. При изменении версии модели или system prompt поведение может измениться непредсказуемо, что затрудняет аудит и отладку.

## Опыт взаимодействия

Пользователь задаёт высокоуровневую цель одним сообщением на русском языке — без указания конкретных файлов или шагов. Агент самостоятельно декомпозирует задачу: сначала исследует структуру проекта через `list_files`, затем ищет нужные паттерны через `search_files`, читает найденные файлы и синтезирует результат в виде Markdown-отчёта.

Шаг верификации через `run_build_check` существенно повышает надёжность: агент не просто создаёт отчёт на основе статического анализа, но и подтверждает, что проект находится в работоспособном состоянии. Пользователь получает ответ, который содержит как результат работы, так и уверенность в корректности проекта.

## Реализованные сценарии

### Сценарий 1 — Usage Analysis

Цель пользователя: найти все места использования класса `ConversationManager` и сохранить их в отчёт.

Цепочка вызовов инструментов:
1. `search_files(pattern="ConversationManager")` → 8 совпадений в 5 файлах
2. `write_file(path="usage_report.md")` → записано 1842 байта

Агент вернул сводку по основным местам использования с указанием файлов и ролей каждого вхождения.

### Сценарий 2 — Project Integrity Check

Цель пользователя: проверить целостность проекта — скомпилировать и зафиксировать результат.

Цепочка вызовов инструментов:
1. `list_files(directory="cli-app/src")` → 24 файла
2. `run_build_check()` → BUILD SUCCESS (6s)
3. `write_file(path="integrity_report.md")` → записано 2104 байта

Агент подтвердил структурную корректность проекта, успешную компиляцию и сохранил итоговый отчёт.
